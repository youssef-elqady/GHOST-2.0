# AUTH-02 — First Admin Bootstrap and AuditLog Implementation Design

Status: approved implementation design; implementation not yet complete.
Branch: `feature/products-inventory-billing`
Scope: one-time first-Admin bootstrap plus durable append-only audit persistence.

## 1. Decisions

- Use the existing ASP.NET Core Identity EF Core integration already referenced by Infrastructure. Do not implement password hashing, password verification, role management, or normalization manually.
- Keep provisioning in a dedicated server-side console host. No HTTP endpoint, API startup seeding, default password, or credential in command-line arguments.
- Use the existing `ApplicationUser`, `IdentityRole<Guid>`, and `GHOSTDbContext`; preserve the seven AUTH-01 Identity table mappings and the existing applied AUTH-01 migration.
- Create only the first Admin and the two approved roles (`Admin`, `Staff`). Do not create a Staff account during bootstrap.
- Persist a general SRS-aligned `AuditLogs` entity, not a duplicate security-only log table.
- Bootstrap user/role changes and its audit row must commit or roll back together.
- Serialize all bootstrap attempts with a SQL Server transaction-owned exclusive application lock acquired before checking whether an Admin exists.
- Recovery is a separate command and is out of scope for this bootstrap implementation.

## 2. AuditLogs schema

| Column | SQL type | Rules |
|---|---|---|
| Id | uniqueidentifier | PK; generated by application |
| UserId | uniqueidentifier NULL | FK to Users.Id, ON DELETE NO ACTION |
| ActorType | nvarchar(16) | Required; only System or User |
| Action | nvarchar(100) | Required |
| EntityType | nvarchar(100) | Required |
| EntityId | nvarchar(128) NULL | Text to support GUID and non-GUID entity keys |
| OldValues | nvarchar(max) NULL | Valid JSON when present; max 16 KiB |
| NewValues | nvarchar(max) NULL | Valid JSON when present; max 16 KiB |
| At | datetimeoffset(7) | Required UTC timestamp |

Constraints:
- Actor invariant: System requires UserId IS NULL; User requires UserId IS NOT NULL.
- OldValues/NewValues must be NULL or valid JSON (`ISJSON`) and each is limited to 16 KiB.
- Index `(EntityType, EntityId, At)` for entity history.
- Index `(UserId, At)` for actor history.
- The user FK restricts deletion; Identity users must be disabled, not deleted.
- The bootstrap audit row uses ActorType=System, UserId=NULL, Action=Admin.Bootstrapped, EntityType=User, EntityId=<new Admin Guid>. The NewValues payload is an allowlisted summary (for example username and role names), never a serialized ApplicationUser object.

## 3. Append-only enforcement

Implement a SQL Server AFTER UPDATE, DELETE trigger on dbo.AuditLogs that throws and rolls back any attempted mutation. This provides a database-level guard even if application code accidentally exposes an update/delete path.

Deployment hardening must additionally grant the application database principal INSERT/SELECT only on AuditLogs and explicitly deny UPDATE/DELETE. The current development connection uses Windows trusted authentication; do not assume its principal is least-privileged. Before production, identify the actual runtime principal and verify its effective permissions. A trigger is not a substitute for least-privilege credentials because privileged principals can disable triggers.

No EF repository/API method for updating or deleting AuditLogs will be added. The domain model will expose creation only; database enforcement remains authoritative.

## 4. Bootstrap transaction and race protection

1. Build the CLI host from secure server-side configuration; never accept a password argument.
2. Prompt for username/full name and read password twice using hidden interactive input. Require explicit confirmation of the one-time bootstrap action.
3. Create a DI scope so UserManager, RoleManager, and GHOSTDbContext share the same scoped context.
4. Begin a SQL Server EF transaction.
5. Execute `sys.sp_getapplock` using a stable resource name such as `GHOST:AUTH:FirstAdminBootstrap`, `Exclusive` mode, `Transaction` owner, and bounded timeout. Treat only non-negative return codes as lock success; fail closed on every negative code.
6. After lock acquisition, query the persisted user-role join for an existing Admin. If one exists, refuse and roll back.
7. Create missing Admin/Staff roles with explicit non-empty Guid IDs and normalized names. Do not silently repair conflicting role records.
8. Create the Admin with Identity UserManager and configured password policy, then assign the Admin role.
9. Insert the sanitized AuditLog row and save.
10. Commit. Any Identity error, SQL error, cancellation, audit failure, or injected failure rolls back user, role assignment, role creation, and audit row.

The transaction must be created from the same scoped GHOSTDbContext used by the Identity stores. Verify this with a test that inspects the transaction and with SQL Server integration tests; do not assume independently constructed contexts share the transaction.

## 5. Password and runtime configuration

- Explicitly configure Identity password length/complexity, unique usernames, lockout, and allowed characters in the CLI host. The chosen policy must be documented and tested.
- Identity's configured password hasher is the only password storage mechanism.
- Passwords are never placed in process arguments, environment variables, config files, logs, exception messages, audit payloads, or shell history.
- Hidden console input must handle backspace and cancellation without echoing typed characters. If stdin is redirected/non-interactive, fail closed rather than falling back to plaintext input.
- Do not print the password or hash. Output only success/failure and the created username/ID as appropriate.
- Do not add JWT, login, refresh tokens, authorization middleware, Staff lifecycle, or ICurrentUser implementation in this slice.

## 6. Test strategy

Add a separate SQL Server integration-test project/harness. Tests must target a disposable database created specifically for the test run; never point tests at the live `GHOST2` database. Require an explicit test connection string and reject a database named GHOST2.

Required SQL Server tests:
- First bootstrap creates exactly one Admin, both approved roles, and one matching audit row.
- Re-running bootstrap refuses and leaves row counts unchanged.
- Two concurrent bootstraps yield exactly one success and exactly one Admin.
- Invalid password creates no user, role assignment, or audit row; role creation must also roll back if it occurred in the transaction.
- Injected failure after user creation and after audit insertion rolls back all bootstrap writes.
- Audit actor constraints, JSON constraints, FK restrictions, and append-only trigger reject invalid writes/updates/deletes.
- Audit payload and captured console/log output contain no password, hash, security stamp, token, or temporary credential.
- Application lock timeout/error fails closed.

Unit tests may cover input validation, result mapping, and sanitization, but cannot replace SQL Server tests for application locks, trigger behavior, and transactional rollback.

## 7. Implementation sequence and safety gates

1. Add AuditLog entity/configuration and SQL Server append-only trigger migration source; generate the migration with the repository's EF Core 10.0.12 tooling locally so the model snapshot/designer are generated, not hand-authored.
2. Review generated migration Up/Down SQL and model snapshot against the existing AUTH-01 snapshot. Confirm it is additive and does not rename/drop/alter existing Identity or business tables.
3. Add the console bootstrap host and transaction/application-lock orchestration.
4. Add SQL Server integration test project and run it only against a disposable test database.
5. Run full solution build/tests and dependency audit; report exact output.
6. Update STATE after each verified milestone.
7. Only after reviewing the generated migration and backup/restore plan, request separate explicit approval before applying it to the user's live GHOST2 database.

## 8. Explicit non-goals

- No change to AUTH-01 migration or its already-applied schema.
- No live database query, migration application, or data mutation as part of this design.
- No bootstrap attempt against live GHOST2 until the migration and CLI are tested and the operator explicitly runs the command.
- No Admin existence claim until a deliberate read-only check is run.
- No JWT/login/refresh, recovery command, API authorization, staff management, shift/session actor binding, or frontend changes.
